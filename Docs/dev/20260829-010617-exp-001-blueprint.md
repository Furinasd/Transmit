# EXP-001 Implementation Blueprint

- Timestamp: 2026-08-29 01:06:17 +08:00
- Status: Design only
- Repository baseline: `feat/exp-001` at `9c0b6f7`
- Scope: implementation design only; no gameplay code or Unreal assets are authorized by this document alone

## Goal

Build EXP-001 as the reusable runtime foundation for L1:

- Complete `Linear Source -> Player -> Linear Receiver` in `L_TestChamber`.
- Support Read/Preview, Capture, Carry, Transfer, Consume, and Room Reset.
- Preserve single ownership, atomic movement, direction, and observable rejection.
- Reach the first clear Capture/Transfer payoff within 40 seconds and the complete loop within 60-90 seconds.
- Pass 20 consecutive Capture/Transfer/Reset cycles without duplication, loss, stale carry state, or orphaned presentation actors.
- Keep C++ responsible for state, validation, transactions, targeting policy, reset orchestration, and stable facts; keep Blueprint responsible for input wiring, authored actor behaviour, presentation, and level assembly.

Explicit non-goals:

- L2 Redirect/Relay, L3 Charger, Angular, Oscillation, GAS, Behaviour Tree, save/load, replication, or a general combat framework.
- Replacing or rewriting the existing third-person template assets.
- Treating EXP-001 as proof that the paper L1 `Source -> Player -> Crate -> Gate` path is complete.

## Current Constraints

- The repository is currently Blueprint-only; no custom C++ module or Motion Transfer implementation exists (`Docs/ARCHITECTURE.md:18-23`).
- `UMotionTransferComponent` must be the only runtime writer of `CurrentMotion`; Blueprint receives query/request APIs only (`Docs/ARCHITECTURE.md:87-91`, `Docs/Decisions/ADR-001-transfer-state.md:21-25`).
- P0 implements Linear only. Direction and Magnitude travel with the state; continuous magnitude versus visible gameplay tiers remains open (`Docs/DESIGN_CONTRACT.md:19-31`).
- Targeting must remain deterministic and must not derive output direction from aim (`Docs/Decisions/ADR-002-interaction-model.md:29-33`).
- Room Reset must restore authoritative state and clear transient targeting (`Docs/ARCHITECTURE.md:191-193`, `Docs/Decisions/ADR-002-interaction-model.md:46-50`).
- `L_TestChamber` and Transmit-specific Input Actions do not yet exist.
- The working tree was clean when this blueprint was written. Existing future user changes remain user-owned and must be rechecked before implementation.
- A known DDC/Zen write-path problem may make commandlets return a non-zero process exit even when Blueprint compilation itself succeeds (`Docs/STATE.md:20-24`, `Docs/STATE.md:70-78`).

Document boundary:

- EXP-001 acceptance in ADR-002 is `Source -> Player -> Receiver`.
- The paper L1 proof in `DESIGN_CONTRACT.md` is `Source -> Player -> Crate -> Gate`.
- This blueprint implements the former and preserves a `Store` endpoint mode for the later Carrier step. It must not silently redefine the L1 contract.

## Design

### 1. Runtime state and stable identity

`FMotionState` contains:

- `EMotionType Type` - `Linear` only in P0.
- `FVector Direction` - normalized world-space direction.
- `float Magnitude` - positive authoritative numeric value.
- `FName SourceId` - stable, authored, room-scoped diagnostic identity.

`SourceId` must never be an `AActor*`. Runtime notifications may contain weak, transient Actor references for immediate presentation, but ownership history, logs, reset reconciliation, and test assertions use `FName SourceId` and `FName ParticipantId`. No raw Actor pointer may be retained across Room Reset.

`Period` and `Phase` remain absent in P0. Adding them later must extend the value without changing ownership or transaction boundaries.

### 2. Magnitude remains Float; compatibility uses derived Gameplay Tags

Raw `Magnitude` remains the source of truth for movement. Blueprint must not contain comparisons such as `Magnitude >= 0.8f`.

Add one central C++ policy exposed through Project Settings, for example `UMotionTransferSettings`:

- Ordered magnitude bands, each with `MinInclusive`, `MaxExclusive`, and one `FGameplayTag`.
- Native tags such as `Motion.Tier.Weak`, `Motion.Tier.Medium`, and `Motion.Tier.Strong`.
- `ResolveMagnitudeTier(float Magnitude) -> FGameplayTag`.
- Editor/startup validation that ranges are ordered, non-overlapping, tags are unique, and every authored P0 Source magnitude resolves to exactly one tier.

`UMotionTransferComponent` exposes the derived tier as a read-only query and uses an `FGameplayTagQuery AcceptedMagnitudeTiers` for Receiver compatibility. The tag is derived on demand and is not stored as a second mutable field in `FMotionState`; this prevents Float and Tag from drifting apart.

Consequences:

- Physics/gameplay movement can continue using the Float.
- Blueprint branches and Receiver authoring use tags/tag queries.
- Global tier tuning occurs in one settings surface rather than in individual Blueprint graphs.
- The visual choice between continuous magnitude and displayed tiers remains reversible.

### 3. Motion ownership component

Every Source, Player, Carrier, or Receiver owns one `UMotionTransferComponent`:

- Private `bHasMotion` and `CurrentMotion`.
- Stable `ParticipantId`.
- Initial state snapshot used by Room Reset.
- Endpoint mode: `Store` or `ConsumeOnReceive`.
- Type, direction, and magnitude-tag acceptance rules.
- Read-only state/compatibility queries.
- Capture, Transfer, Consume, and Reset transaction entrypoints.
- State fact and transaction result delegates.

Blueprint may request an operation or react to a delegate, but it cannot assign, clear, or fabricate `CurrentMotion`.

### 4. Actor-level interface

Keep `IMotionTransferable` on the Actor, not on the Component.

It exposes:

- `GetMotionTransferComponent()`.
- `CanCaptureMotion(Context)`.
- `CanReceiveMotion(State, Context)`.

The interface remains necessary because future Actors need contextual rules that are not properties of the generic component. For example, a Charger can override `CanCaptureMotion` to allow Capture only during its committed dash window. EXP-001 Actors use the default component-backed rules.

Candidate discovery may first check `Actor->Implements<UMotionTransferable>()`; it must not bypass Actor overrides by directly treating every found component as transferable. `FindComponentByClass` may be used inside the interface's default implementation, not as a replacement for the interface contract.

### 5. Transaction lock and notification ordering

The transaction boundary uses two distinct guards:

1. `bTransactionInProgress` protects validation and state mutation.
2. `bDispatchingNotifications` protects notification ordering only; it is not a state lock.

Commit sequence:

1. Reject if another state transaction is active.
2. Validate requester, Source, Player, Target, compatibility, range, occlusion, and current ownership.
3. Copy the moved state into a local immutable result snapshot.
4. Set `bTransactionInProgress = true`.
5. Clear the previous owner and assign or consume at the next owner.
6. Verify the postconditions: exactly one live owner, or zero after a valid Consume; state identity, direction, and magnitude are unchanged.
7. Build one immutable `FMotionNotificationBatch` describing all post-commit facts.
8. Set `bTransactionInProgress = false`.
9. Enqueue the notification batch and flush notifications in FIFO order.

The lock is therefore always released before any delegate broadcast. Broadcast is notification, never intervention.

If a listener requests another transfer during a broadcast:

- It is evaluated as a new independent transaction against the already committed state.
- Normal cooldown, verb state, range, or compatibility may reject it.
- If it succeeds, its notification batch is appended to the FIFO queue.
- `bDispatchingNotifications` prevents recursive flushing, so the new batch broadcasts only after the current batch finishes.

This keeps data re-entrancy safe without allowing nested broadcasts to scramble observer ordering.

Recommended within-batch order:

1. Previous owner state changed/lost.
2. New owner state changed/gained, or Receiver consumed.
3. Verb-level `Captured`/`Transferred`/`Consumed` result.
4. Debug/telemetry record.

No observer may veto or roll back an already committed transaction.

### 6. Target scoring and sticky target

`UMotionInteractorComponent` collects Actor-level `IMotionTransferable` candidates inside the configured aim cone and range, then evaluates occlusion and compatibility.

For each candidate:

```text
RawScore = (DotProduct * WeightA) - (NormalizedDistance * WeightB)
```

- `DotProduct` is camera-forward dot normalized direction-to-target.
- `NormalizedDistance` is clamped to `[0, 1]` using the targeting range; raw Unreal units never leak into tuning.
- `WeightA`, `WeightB`, `StickyBonus`, cone, range, and stickiness timeout are editor-exposed C++ properties.

Switch rule:

```text
Keep CurrentTarget while:
NewCandidate.RawScore <= CurrentTarget.RawScore + StickyBonus

Switch only when:
NewCandidate.RawScore > CurrentTarget.RawScore + StickyBonus
```

The current target's effective score is therefore `RawScore + StickyBonus`; the bonus is applied exactly once. "Absolute exceed" means crossing this threshold, not applying a mathematical `abs()` function.

Sticky weight applies only while `CurrentTarget` remains in range, unobstructed, valid for the current verb, and alive. Hard invalidation removes stickiness immediately. Equal scores use stable `ParticipantId` as the final deterministic tie-breaker rather than memory address or Actor pointer value.

When no legal target exists, the highest-scoring inspectable invalid candidate may still drive rejection presentation, but it does not receive legal-target stickiness.

### 7. Room Reset and presentation lifetime

`AMotionRoomResetController` holds an explicit participant list and orchestrates:

1. Block new requests and clear current targeting.
2. Broadcast `PreReset` so Blueprint stops Timelines, movement, audio loops, and transient effects.
3. Restore participant transforms.
4. Restore every Motion Component's initial state.
5. Close/reset Receiver and room completion presentation.
6. Clear registered transient objects.
7. Broadcast `PostReset`, rebuild persistent indicators, and re-enable input.

Presentation rules:

- Prefer activating/hiding components already owned by Source, Player, Receiver, or Room Controller.
- Prefer Niagara systems with self-managed finite lifetimes.
- Presentation Blueprint must not freely Spawn unmanaged world Actors.
- If an Actor must be spawned, it must register immediately with the Room Controller's transient cleanup list.
- The cleanup list stores weak object references; Reset destroys or returns each still-valid transient to its pool and then clears the list.
- A transient visual Actor may never carry authoritative Motion State or be used as `SourceId`.

### 8. Blueprint content

Create new isolated assets under `Content/Transmit/`:

- `BP_TransmitCharacter`: child of the template Character; owns Motion and Interactor components; binds actions; displays Carry state.
- `BP_TransmitPlayerController`: child of the template Controller; installs `IMC_Transmit` in addition to the parent mapping context.
- `BP_TransmitGameMode`: selects the Transmit Character/Controller only for the test map.
- `BP_LinearSource`: starts with authored Linear Motion; uses deterministic authored movement; stops on state loss.
- `BP_LinearReceiver`: consumes matching Linear Motion and activates the room result; its Blueprint logic branches on Gameplay Tags/tag queries, never raw Magnitude.
- `L_TestChamber`: one normal path plus occluded, incompatible, and overlapping candidate fixtures.

Do not modify template Blueprint assets unless a later verified limitation makes inheritance impossible.

## Interfaces

| Interface/type | Producer | Consumer | Contract |
| --- | --- | --- | --- |
| `FMotionState` | Source component | Transaction/component queries | Linear, normalized direction, positive Float magnitude, stable `FName SourceId` |
| Magnitude resolver | `UMotionTransferSettings` | Component, Receiver, presentation | Float maps to exactly one derived `FGameplayTag` |
| `FMotionTransferResult` | Transaction | Input/presentation/tests | Success, verb, rejection, immutable state snapshot, stable participant IDs, optional weak transient Actor refs |
| `FMotionNotificationBatch` | Completed transaction | Notification queue | Immutable, FIFO, created while locked and broadcast after unlock |
| `IMotionTransferable` | Actor | Interactor/transaction | Actor-level component lookup and overridable capture/receive rules |
| Capture request | Interactor | Player Motion Component | Source has state, Player empty, commit-time validation |
| Transfer request | Interactor | Player/Target components | Player has state, Target compatible, aim never supplies direction |
| Consume result | Target component | Receiver presentation | Player empty, transferable state lifecycle ended, function event emitted |
| Reset request | Room Controller | Components and Blueprint presentation | No active transaction; deterministic PreReset -> restore -> cleanup -> PostReset |

Stable rejection identifiers must include at least: `SourceEmpty`, `CarrierOccupied`, `OutOfRange`, `Occluded`, `IncompatibleType`, `IncompatibleDirection`, `IncompatibleMagnitudeTier`, `TargetInvalidated`, `TransactionBusy`, and `CooldownActive`.

## Data Flow

```text
Camera/Input
    |
    v
UMotionInteractorComponent
    | gather Actor interfaces
    | RawScore + CurrentTarget StickyBonus
    | preview
    v
Commit-time validation
    |
    v
[Transaction Lock ON]
Source -> Player -> Receiver/Consume
verify postconditions
create immutable NotificationBatch
[Transaction Lock OFF]
    |
    v
FIFO Notification Queue
    |
    +--> component state facts
    +--> verb result
    +--> Blueprint presentation
              |
              +--> owned Components / managed Niagara
              +--> registered transient Actors only
```

Failure paths:

- Preview becomes stale: commit revalidates, returns `TargetInvalidated`, changes no state.
- Current target becomes invalid: sticky bonus is removed immediately and selection is recomputed.
- Listener requests a new operation during broadcast: it becomes a new transaction; its notifications queue behind the active batch.
- Receiver rejects type/direction/magnitude tier: Player retains the state.
- Reset is requested during mutation: reject/defer until the transaction ends; never reset half a transaction.
- Reset is requested during notification dispatch: enqueue one Reset request to execute after the current notification batch, preventing presentation teardown in the middle of a batch.
- Presentation spawn is unavoidable: register it before the next frame can expose it to Reset.

## Migration

There is no persisted schema, save data, or network migration. The safe Blueprint-only to hybrid-project order is:

1. Recheck Git status and preserve user-owned changes.
2. Add and compile the empty `passely` Runtime module and targets.
3. Add Motion types, settings/tags, component, Actor interface, transaction queue, interactor, reset controller, and C++ tests.
4. Validate native tags/settings before any Blueprint depends on them.
5. Create only new Blueprint/Input assets under `Content/Transmit/`.
6. Create `L_TestChamber`; keep the existing startup map unchanged until the new map passes PIE.
7. Run reset/readability gates before accepting ADR-001/ADR-002 or starting L2/L3.

No Data Asset stores per-instance Motion State. Central tier tuning belongs to Project Settings; presentation assets may be introduced later only for demonstrated reuse.

## Implementation Stages

1. **Native module and policy gate**
   - Add module/targets, native Gameplay Tags, magnitude settings, and validation.
   - Exit: Editor target builds; tier boundaries and invalid settings tests pass.
   - Rollback boundary: no Blueprint references native classes yet.

2. **Ownership and notification gate**
   - Add state, component, Actor interface, atomic transactions, unlock-before-broadcast, and FIFO notification batches.
   - Exit: ownership, rejection, consume, re-entrant listener, event order, and 20-cycle logic tests pass.

3. **Targeting gate**
   - Add candidate collection, RawScore, CurrentTarget StickyBonus, hard invalidation, preview, and stable tie-breaks.
   - Exit: overlapping target tests show no frame-to-frame oscillation and switch only across the defined threshold.

4. **Reset/lifetime gate**
   - Add ordered reset and transient registry.
   - Exit: restored state/transform, empty Player, closed Receiver, zero registered/live orphan transients after 20 cycles.

5. **Playable EXP-001 gate**
   - Create isolated Transmit Blueprint/Input assets and `L_TestChamber`.
   - Exit: Source -> Player -> Receiver works in PIE with valid, invalid, occluded, and overlapping cases.

6. **Readability acceptance gate**
   - Tune only presentation, sticky weights, and central magnitude bands.
   - Exit: first player completes in 60-90 seconds and explains that Motion, including its direction/magnitude, moved between owners.

Definition of Done:

- Native build and focused automation pass.
- Blueprint compilation and Map Check pass, with DDC process status interpreted explicitly.
- `L_TestChamber` passes normal and rejection paths in PIE.
- 20/20 Reset cycles preserve ownership and leave no transient presentation objects.
- No Blueprint writes Motion State or compares Magnitude against a literal threshold.
- No persistent identity uses an Actor pointer.
- Blind-test evidence is recorded before L2/L3 work begins.

## Verification

Static and review checks:

- Public Blueprint API contains queries and requests but no writable `CurrentMotion`.
- `IMotionTransferable` is implemented by Actors.
- Direct component lookup does not bypass Actor-level rule overrides.
- Blueprint graphs contain no raw Magnitude threshold logic.
- Spawn nodes for gameplay presentation either do not exist or immediately register the result with Room Reset.

Focused automation:

- Capture moves the same `SourceId`, Direction, and Magnitude from Source to Player.
- Transfer/Consume leaves the correct postcondition and derived magnitude tag.
- Every rejection preserves the current owner.
- Float values exactly at each band boundary resolve deterministically.
- Invalid or overlapping settings fail validation.
- Transaction lock is false when the first delegate executes.
- A delegate-triggered second transaction succeeds/rejects independently and its notification batch remains FIFO.
- Current target remains stable until `New.RawScore > Current.RawScore + StickyBonus`.
- Invalidating Current Target removes stickiness immediately.
- Reset during mutation or notification follows the documented defer/reject rule.
- 20 cycles retain no dead weak references or unmanaged transient Actors.

Editor/runtime verification:

- Build the UE 5.8.1 Editor target.
- Run focused Motion Transfer automation.
- Compile all Blueprints and run Map Check.
- PIE normal loop, empty-hand Transfer, occupied-player Capture, incompatible magnitude tier, wrong direction, occlusion, stale target, and overlapping-target camera sweep.
- PIE Reset while carrying, after Receiver consumption, during active presentation, and after a registered transient Spawn.
- Record 20/20 cycles and the first-player comprehension result.

Compilation is not gameplay acceptance. Windows evidence does not prove macOS compatibility.

## Rollback

- Stage 1: remove/revert native module registration only before Blueprint references exist.
- Stages 2-4: keep the module loadable and revert the bounded feature code; no assets or persisted data require migration.
- Stage 5 onward: revert new `Content/Transmit/` assets before removing any referenced native class.
- If tier tuning is faulty, restore the prior Project Settings band table; raw Float state remains compatible because tags are derived rather than persisted.
- If notification dispatch fails, disable presentation listeners while preserving the committed state/log evidence; repair ordering forward rather than attempting event-driven rollback.
- If Reset finds unmanaged transients, stop acceptance, register/fix the exact producer, and repeat the full 20-cycle gate.
- Existing template maps and Blueprints remain the fallback launch path throughout implementation.

No persisted data operation is irreversible. The primary rollback hazard is removing native classes while Blueprint assets still reference them, so asset rollback must precede module rollback.

No unresolved decision blocks the internal interfaces in this blueprint. Exact tier thresholds, targeting weights, StickyBonus, and visual timing are centralized tuning values to be established through `L_TestChamber`, not Blueprint-local constants.
